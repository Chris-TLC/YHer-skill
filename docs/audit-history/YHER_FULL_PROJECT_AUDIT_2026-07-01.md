## 0. 一句话结论

YHer 不是空想项目，已经有真实数据资产、真实工程沉淀和真实产品洞察；但它还不是一个可以商业化推广的产品。现在最正确的方向不是继续扩成“教育操作系统”，而是把化学先压成一个极窄但可验证的闭环：上海高中化学单知识点诊断 -> 推荐具体视频 -> 看后验证 -> 更新画像 -> 下次更准。

如果从 YC 视角看：创始人洞察强、行动速度快、问题真实，但外部需求证据还弱。当前最大风险不是技术做不出来，而是继续把“宏大愿景、全科托管、AI 班主任、99% 精度”提前装进 MVP，导致没有一个真实学生愿意连续用、愿意付费、愿意把 3 小时交给它。

## 2. 时间线与方向演化

### 2026-06-22：初衷是 AI 私教，不是普通答疑工具

最早的核心问题是：能否做出一个让高中生愿意把 3 小时交给 AI 的一对一私教。用户标准不是“页面好看”或“模型回答长”，而是“比自己乱学强很多，比普通网课更像有人管我”。

当时已经形成三阶段愿景：

1. 单科化学私教闭环。
2. 多学科统一画像与协作。
3. AI 班主任/教育操作系统。

这个愿景方向仍然成立，但不能作为当前 MVP 的交付范围。

### 2026-06-23 至 2026-06-24：多学科并行与成本焦虑

项目一度同时处理化学、数学、物理。数学切题、化学解题、物理接力脚本并行跑。这个阶段证明了用户有很强的执行欲望，也积累了多学科资产；但它同样暴露了一个问题：化学闭环尚未稳定，多学科并行会放大数据质量、成本、架构和注意力问题。

当前“化学先做成可用产品，数学物理暂缓”的决策是正确的。

### 2026-06-25：Demo 被真实体验击穿

早期 Demo 的问题集中在：

- 诊断不递进。
- T1-T6 任务队列不够自动化。
- 讲解太表面。
- 变式不够应试化。
- UI 不够克制。
- 页面未经过真实点击验证。

这是项目很重要的一次转折：从“AI 说得像老师”转向“诊断、闸门、任务状态、题目质量、体验闭环”。

### 2026-06-26：战略转向到 AI 内化上海真题

题库质量诊断发现旧题库存在大量复合题、损坏题、结构化不完整题。项目先后经历三轮思路：

1. 纯 AI 动态出题。
2. 500 道黄金题库打底。
3. 最终定稿：AI 内化全部上海真实试卷，提取出题规律，再受控生成。

用户否定 500 道黄金题库的判断是对的：它适合做评测集和金标准样本，不适合作为核心题源。核心题源必须来自更大的真题分布和题型规律。

### 2026-06-27：旧路线被明确覆盖

`CURRENT_DECISIONS.md` 明确了几件事：

- AI 出题验证优先。
- 不再以“一化儿教学方法、节奏、认知脚手架”作为 AI 自主发挥核心目标。
- AI 负责诊断、推荐、验证、画像和出题质量控制。
- 化学先做到可用产品。
- 旧文档保留为历史，不因被推翻而删除。

这份文件现在应当被视为高优先级决策源。

### 2026-06-28：Agent loop 事故

项目发生过一次严重工程协作事故：高频轮询日志、反复重启/清理管道、写入明文 API key、成本和 token 失控。这次事故给项目留下了正确纪律：

- 禁止高频轮询。
- 禁止自动重启管道。
- 禁止清空进度和输出。
- 禁止把 API key 写入代码或聊天。
- 连续失败 2 次必须停止并报告。

这是必须长期遵守的生产纪律，不只是一次事故复盘。

### 2026-06-29 至 2026-07-01：数据完成与端到端修 bug

v3 视觉管道完成 210/210 文件，FastAPI 和静态前端进入可走查状态。AI 诊断题库从 90 补到 119/137，用户拍板不再重跑，接受 KG 兜底。真正 0-AI 的硬空洞为：

- 溶液三大守恒。
- 工艺流程。
- 实验综合大题。

这个决策也正确：继续重跑只是在烧钱。下一步不是再跑一遍，而是人工金标准题、真题抽题或针对大题型专项生成器。

## 3. YC 视角重评估

### 3.1 需求真实性

这个项目的问题是真实的：高中理科复习中，学生常常不知道自己到底卡在哪里，只能刷题、看视频、问老师或上补习班。用户本人就是目标用户，这一点很强。

但 YC 会追问：除了创始人自己，还有多少具体学生已经表现出强需求？他们是否愿意连续使用？是否愿意付费？是否在产品坏掉时主动催你修？目前项目还缺这类外部证据。

结论：问题真实，需求强度未被外部验证。

### 3.2 状态 quo 才是真竞品

这个项目的真正竞品不是另一个 AI App，而是学生现在已经在做的组合：

- B 站看一化儿或其他老师视频。
- 刷学校卷、教辅、真题。
- 问同学、老师、家教。
- 用拍照搜题或大模型问答。
- 买学习机或报补课班。

如果 YHer 不能让学生明显感觉“我本来要乱找半天，现在它直接定位我该看哪一集、做哪类题、怎么验证”，那它就不是刚需。

### 3.3 最窄 wedge

当前最窄、最合理的 wedge 是：

> 上海高中化学学生，在一个具体知识点上卡住时，用 YHer 做 5 分钟诊断，拿到一组视频/练习/验证任务，并在 30 至 60 分钟内确认自己是否真的进步。

更窄一点：

> 化学平衡/电化学/盐类水解这类高频痛点中的一个，先做到“比自己找视频强很多”。

不要用“AI 班主任”“教育操作系统”“全科托管”作为第一阶段对外承诺。它们可以是内部北极星，但不是 MVP 的销售话术。

### 3.4 创始人优势

优势很明显：

- 创始人是目标用户，且具备强烈痛感。
- 对“一化儿”等内容资源的理解有真实使用经验，不是抽象调研。
- 对产品体感非常敏感，能识别“人机味”“假数据”“花哨 UI”。
- 愿意推翻旧方案，说明不是死守自己最初想法。
- 执行速度极快，十天内已形成真实数据、后端、前端、题库和评测雏形。

YC 会喜欢这种 founder-market fit。

### 3.5 创始人风险

风险也同样明显：

- 容易把终局形态提前塞进 MVP。
- 容易被“数据量、节点数、99%”吸引，而不是被“一个学生是否真的变强”约束。
- 容易让 AI Agent 大规模跑任务，造成成本/状态失控。
- 当前缺少真实外部用户访谈、付费实验和留存数据。

创始人要从“做一个很完整的系统”切换到“手动服务 5 个学生，让他们离不开这个流程”。

### 3.6 商业模式判断

“订阅 + 学习托管额度”的方向合理，但目前不能当作已验证商业模式。更诚实的状态是：商业模型假设成立，但支付意愿未验证。

建议第一阶段不要过早设计复杂档位。先做三个实验：

1. 5 个同校或同城学生，免费但要求完整使用记录和访谈。
2. 3 个学生尝试低价付费，例如 19 元/周或 49 元/月，只卖化学一个场景。
3. 让学生在一次真实复习任务中选择：继续自己找视频，还是让 YHer 管一小时。

付费不是为了赚钱，是为了测痛感。

### 3.7 竞争判断

已有竞品扫描认为“三点全中”的直接对手不明显：软件订阅额度制、高中理科垂直、托管闭环/AI 班主任。但每个单点都有强对手，大厂可以很快进入。

YHer 真正可能形成壁垒的不是“用了 LLM”，而是：

- 上海化学真题/知识点/视频路由的高质量垂直数据。
- 诊断题、rubric、真题标准解、学生画像之间的闭环。
- 对学生真实体感的反复打磨。
- 早期用户反馈形成的细粒度 product taste。

如果只拼“AI 问答/讲题”，没有壁垒。

## 4. 产品质量审计

### 4.1 当前产品闭环

现在已有的主链路是：

1. 选知识点/创建 session。
2. 逐题诊断。
3. 根据回答更新 mastery。
4. 展示能力画像。
5. 推荐视频。

这是对的，且比单纯聊天工具更接近“私教”。不过它还没有完整闭环：

- 看视频后的验证页仍未完成。
- Wow2 能力提升动画仍未完成。
- 成长 Dashboard 仍未完成。
- 长期画像还未接近真实生产形态。
- 没有真实学生全流程使用数据。

### 4.2 已经变好的地方

- 前端已不再重复同一道 `first_question`。
- `/profile` 已从诊断历史聚合真实雷达图数据，不再默认假数。
- 含 `/` 节点视频 URL 问题已修。
- AI 诊断题取题已有三层 fallback：自身、子到父、父聚合子节点。
- FastAPI 成为 HTTP 与引擎的翻译层，为后续 App 留出接口边界。

### 4.3 仍然最危险的体验问题

- 诊断题质量在高难节点上仍弱，尤其是三大硬空洞。
- 诊断题大量集中在 T2 和选择题，不足以支撑“逐层诊断”的心理预期。
- 视频推荐是否真的“刚好”尚未经过真实学生验证。
- 前端缺少系统的浏览器回归测试，移动端体验未知。
- 目前还没有“看完视频后确实提升”的证据链。

## 5. 数据与题库质量审计

### 5.1 数据资产是真实优势

v3 管道、6438 道结构化题、135 节点 KG、139 个出题规律文件、119 节点 AI 诊断题库，这些都是真实资产。很多 AI 教育项目停留在 prompt 和 UI，YHer 至少已经走进了领域数据层。

### 5.2 题库入口缺少中心质量门

`core/data/item_repository.py` 当前会加载 `data/item_bank/*.jsonl` 下所有 JSONL。它不会根据 `verification_status`、`confidence`、复合题、图依赖、rubric 完整度做统一过滤。

这在原型阶段可接受，但在诊断和教学进入真实用户前，必须加一个中心质量门。否则低质量题会随机进入教学引擎，前端再漂亮也兜不住。

建议给每道题建立可查询的质量状态：

- `usable_for_diagnosis`
- `usable_for_teaching`
- `needs_image`
- `needs_manual_review`
- `rubric_complete`
- `source_confidence`

### 5.3 AI 出题验证仍是样本级，不是产品级

`generated_v1.jsonl` 只有 53 行。平均分高、硬伤少，说明生成器方向可行；但 53 题不能证明全节点、全题型、全难度可用。

AI 出题要成为产品资产，需要固定评测集，而不是只看模型自评/对抗验证分。

建议：

- 先建立 100 道人工金标评测题，不作为题源，只作为判定生成题质量的标尺。
- 每次改 prompt 或生成器，跑同一套评测维度。
- 让真人学生或老师对部分生成题做 blind review。

### 5.4 AI 诊断题库的正确决策

119/137 后停止重跑是对的。每轮新增递减，说明问题不是“多跑几次”能解决。接下来应该：

- 对 3 个硬空洞人工补金标准诊断题。
- 对图依赖节点优先真题抽题，不强迫纯文本生成。
- 把大题型拆成小诊断动作，例如“入口判断”“变量关系”“守恒式列法”“答案结构”。

## 6. 架构与代码设计审计

### 6.1 架构正向信号

当前工程已经有几条值得保留的好边界：

- `apps/api_server.py` 作为 HTTP 到引擎的翻译层。
- `core/tutor/session_orchestrator.py` 作为会话编排层，和 UI 解耦。
- `core/tutor/diagnose_engine.py` 把诊断、rubric、mastery 估计集中处理。
- `scripts/ai_diagnostic_provider.py` 把离线预生成题和运行时读取分离。
- `scripts/generate_questions_phase1.py` 里有生成器、对抗验证、无图硬闸门、重生逻辑。

这不是随手堆 demo，而是在往可演进架构走。

### 6.2 诊断引擎方向正确

`DiagnoseEngine` 的关键设计是“客观 rubric + LLM 判定 + must_have 封顶”。这是项目最重要的技术方向之一，因为它避免了 LLM 单纯自评 mastery。

已通过的测试里包含：

- `rubric_verdict_overrides_keyword`
- `rubric_must_have_cap`
- `no_fake_pass`
- `vicious_cycle`
- `orchestrator_fallback`

这说明你们已经在防真实教育产品会遇到的错误，而不是只测 happy path。

### 6.3 主要工程风险

P0 风险：

- 工作树过脏，成果未纳入稳定版本控制。
- README 与最新决策冲突，仍在强调“模仿杰哥讲题套路”。
- 当前没有生产级账号、权限、会话隔离、隐私策略。
- 本地存在 `.env` 和 `.env.bak.*`，虽然 gitignore 和 tracked 文件看起来未提交密钥，但本地密钥卫生必须继续保持。

P1 风险：

- ItemRepository 无中心质量过滤。
- 前端缺少自动化浏览器回归。
- API 端点没有稳定契约测试。
- 题目生成和诊断题库缺少长期评测仪表盘。
- 依赖文档不完整，v3 管道相关依赖未完全体现在 `requirements.txt`。

P2 风险：

- 多套旧架构文件与新方向并存，AI 和人都容易读错。
- 有多个 demo/进度/仪表盘应用，入口不够清晰。
- `TODO` 里仍有 SupabaseStore、云端检索等后续项，但当前 MVP 不该急着做。

## 7. Design 审计

### 7.1 方向正确

用户多次校正 UI 方向：Apple 克制、无 emoji、无模型名、不做花哨营销页。这一点非常适合教育工具。对高中生来说，信任感比炫技重要。

### 7.2 当前缺口

- 只有静态 HTML 原型和部分页面，不是完整产品面。
- 没有足够移动端验证。
- 没有系统列出 loading/error/empty/offline/题目过长/公式渲染失败状态。
- 视觉设计规范已存在，但未完全变成可复用组件或测试标准。

### 7.3 设计评分

- 视觉方向：7/10。
- 当前实现完整度：5/10。
- 学生真实流程可用性：待实测，不能凭代码评分。

## 8. DX 审计

### 8.1 当前 DX 最大问题

新开发者打开 README 会被旧定位误导。README 仍写“模仿杰哥讲题套路”“杰哥风格”，但最新决策已经明确：不做口癖/风格模仿，视频是资源和路由对象，AI 做诊断、推荐、验证、画像和质检。

这会造成严重方向偏差。

### 8.2 快速上手不够可信

README 的快速上手仍偏旧 Streamlit/RAG 版本。当前真实 demo 需要 FastAPI、静态 HTML、v3 数据、AI 诊断题库、多个数据目录。缺少一个“当前有效入口”：

- 如何启动后端。
- 如何打开前端。
- 如何确认 API 健康。

### 第 3 至 5 天：完成一个端到端学生闭环

只做一个闭环：

1. 选知识点。
2. 诊断 3 至 5 题。
3. 输出真实画像。
4. 推荐视频。
5. 看后做验证题。
6. 显示是否提升。
7. 记录下次建议。

不要做全科，不做班主任，不做复杂 dashboard。

### 第 6 至 8 天：修质量门和硬空洞

- 给 item bank 增加可用性过滤。

### 第 9 至 14 天：5 个真实学生试用

每个学生只问 4 个问题：

1. 你原本会怎么复习这个知识点？
2. YHer 哪里比你原本方法更省事？
3. 哪一步让你不信任？
4. 你愿不愿意下次复习继续用？愿意为这个功能付多少钱？

核心指标：

- 是否完成一次 30 至 60 分钟学习闭环。
- 是否主动说“推荐的视频/题确实对我有用”。
- 是否愿意下次复用。
- 是否愿意低价付费。

## 16. 最终判断

继续做，但要收窄。

YHer 当前最有价值的不是“AI 能讲化学”，而是“它可能知道学生现在该看哪段视频、做哪道题、补哪个认知断点”。这个定位比 AI 老师模仿更强，也更符合用户最新决策。

接下来两周的唯一目标应该是：让 5 个真实高中生在上海化学一个窄场景里完成一次闭环，并愿意说“这个比我自己乱找资料更有用”。如果这句话拿不到，再多节点、再多模型、再多页面都不算进展。
